# Device enrollment and trust model

## Current alpha.7
The Host owner token is loopback-only. Per-device reader tokens are random 256-bit secrets; only SHA-256 digests and minimal metadata are retained in RAM. Grants expire after 24 hours, maximum 32; restart invalidates all. Initial LAN access is a separate reader grant, not the owner token. A local owner dashboard can issue, list and revoke grants. REST verifies every request; WS validates the grant before sending each sample (one in-flight frame may complete). A device identity is a label and bearer credential, not proof of physical hardware identity.

## Invitation protocol (alpha.8 implementation; CI verified)
The owner creates an invitation with POST /api/v1/devices/invitations (JSON name). It returns a two-minute URL fragment with invitation ID and secret. LAN client POST /api/v1/enroll/claim with id and secret consumes the invitation secret and receives a new claim secret and six-digit comparison code. Owner GETs invitation metadata, compares the code separately with the intended device, and POSTs the exact code to /api/v1/devices/invitations/{id}/approve. Client POST /api/v1/enroll/finish with claim secret yields 202 until approval and 201 with reader token once; replay is rejected. Owner can DELETE invitation. Maximum eight outstanding invitations, only hashed secrets in memory. The comparison code is not an authentication credential by itself. Public routes are restricted to configured LAN TLS listener, not loopback. Browser enrollment UI implemented: copy invitation privately, open on trusted HTTPS tablet, accept, compare the code on the tablet, type it into owner panel, then check approval. QR PNG rendered locally in Host using `Net.Codecrete.QrCodeGenerator` 3.2.1 (exact pinned NuGet version). MIT notice included in package. No remote QR service; image contains only the two-minute invitation and is cleared from owner UI, not stored on disk. Independent decoding/camera acceptance pending. Upstream https://github.com/manuelbl/QrCodeGenerator/tree/v3.2.1 ; package https://www.nuget.org/packages/Net.Codecrete.QrCodeGenerator/3.2.1 . Interactive browser acceptance pending.

## Next: QR enrollment
- The QR is generated locally on the owner PC without remote services, URLs to third-party QR generators, analytics or external fonts. Review the license, provenance and dependency before bundling an encoder.
- Prefer a short-lived single-use high-entropy invitation over putting a 24-hour reader credential into a QR. Bind it to the specific configured HTTPS origin, maximum lifetime two minutes, cap outstanding invitations, permit explicit cancellation. Generate and view only from authenticated loopback owner UI. Never encode the owner token, Apollo credentials or PFX password.
- The tablet must establish trust in the HTTPS certificate before presenting the secret; no trust-warning bypass. Browser invitation data should be in a URL fragment that is removed from history and submitted over HTTPS in a bounded POST body. Native Android may use a dedicated scanner and an independently verified certificate trust flow.
- Perform atomic one-time redemption with expiry, bounded attempts and no replay, including concurrent requests. Only issue telemetry reader grants. Do not automatically grant input, Apollo, administrative or Windows control privileges. A scanner that sees the invitation first may redeem it, so display an explicit owner pairing confirmation design before enabling enrollment on shared networks.
- Do not log secrets or store raw invitation/reader tokens on the server. Test expiry, concurrent redemption, revocation, foreign origin, wrong host, capacity, invalid certificate and disconnect/reconnect.
- Avoid persistent browser bearer storage. Android should use OS-protected credential storage after explicit enrollment. On the Host, design a versioned minimal hashed-grant store with restrictive ACLs, atomic replacement, bounds, expiry, corruption handling and explicit revoke-all. Do not persist owner credentials or accept arbitrary file paths from the network. Until rollback and recovery tests pass, retain the RAM-only model.

## Acceptance gates
No automatic TLS CA installation, firewall changes, LAN exposure of administrative APIs or hardware configuration changes. QR flow implemented, pending CI/interactive acceptance. Durable grants and Android credential storage remain unimplemented. Actual Lenovo certificate trust and enrollment must be validated on target hardware.

## Durable store groundwork

A pure schema v1 codec (GrantStoreCodec) accepts a maximum of 32 records, 32 KiB, exact JSON fields and uppercase SHA-256 digest strings. It rejects duplicate IDs/digests, empty owner ID, invalid names, malformed fields and expiry beyond the current 24-hour issuance window; expired records are filtered at read. It intentionally does not open files, trust local filesystem metadata, authenticate stored contents or change live grants. Next choose OS-protected integrity/confidentiality, fixed per-user path, exclusive owner lock, atomic replacement and fail-closed behavior on storage failure. Test restart, revoke-before-crash, corruption, ACL/reparse safety and rollback. Do not enable persistence until these gates are satisfied.

## Protected store primitive (alpha.9)

The Windows-only store uses `System.Security.Cryptography.ProtectedData` 10.0.15 with CurrentUser scope and fixed application entropy. Default path is `%LOCALAPPDATA%\\VeyPanel-GrantStore-v1`; directory must be owned by the current SID with protected user-only inherited ACL. Existing reparse points are rejected; one process holds an exclusive lock. Save creates a flushed transaction marker, writes bounded ciphertext to a new file, flushes and moves it over the authoritative file in the same directory, then removes the marker. Startup refuses interrupted transactions, not automatic backup recovery. DPAPI protects confidentiality/integrity against ordinary other-account access, not same-user/admin tampering or rollback to an older valid encrypted file. Filesystem metadata durability during abrupt power loss is not established. This primitive is not wired into the live registry yet. CI tests are isolated under the current user profile; no existing user store is touched.
